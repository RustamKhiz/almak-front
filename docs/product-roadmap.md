## R1. Пользователи и роли

### Поведение

Существующий аккаунт сохраняет ID, логин и пароль и получает роль `admin`. Создаются ровно два новых аккаунта `manager`. В первой версии обе роли имеют одинаковый полный доступ к существующим функциям CRM: заказы, товары, оплаты, скидки, удаление, справочники, аналитика, документы, черновики и помощник.

Роль пока служит основой для будущих ограничений. Не вводить скрытых ограничений менеджерам, в том числе на доступ к чужим заказам, без отдельного согласования. Авторство действий и роль — разные понятия.

### План реализации

1. Добавить `role` в модель пользователя и миграцию со значениями `admin` / `manager`. Новым обычным пользователям назначать `manager`; текущий аккаунт повысить по явно выбранному существующему ID. Не повышать все старые записи автоматически.
2. Исправить `ensureDefaultUser`: не удалять существующих пользователей, не сбрасывать пароли, не менять назначенную роль при каждом запуске. Отдельно проверить сохранение админа после повторного старта приложения.
3. Добавить получение текущего профиля, например `GET /me`: ID, логин, отображаемое имя при необходимости, роль и доступные действия. Проверять существование пользователя и актуальную роль на сервере; JWT не должен быть единственным источником устаревших прав.
4. Ввести централизованную таблицу возможностей. Пока для обеих ролей выдать все существующие действия. Дальнейшее ограничение выполняется в одном месте на бэке; фронт использует тот же результат для отображения действий.
5. Создать два аккаунта повторяемой административной командой: уникальные логины, индивидуальные пароли, bcrypt. Повтор команды не создаёт дубликаты и не меняет уже выданные пароли. Начать без отдельного экрана управления пользователями.
6. Показывать имя/логин и роль текущего пользователя в интерфейсе. Поддержать профиль в обоих потоках входа и обновления сессии: веб и Electron.
7. Добавить автора/редактора к новым черновикам и записям изменений заказов. Старые действия не приписывать текущему админу задним числом.

### Проверка готовности

- Текущий пользователь входит прежним способом и имеет полный доступ.
- Оба менеджера входят в вебе и Electron и получают тот же набор действующих возможностей.
- Повторный запуск/миграция не удаляет пользователей, не меняет роли и пароли.
- API не доверяет переданным клиентом `userId`, роли или списку прав.
- Изменение роли на сервере учитывается согласно выбранному механизму актуализации, а не только после истечения старого JWT.

### Решить перед реализацией

Подтверждены логины: `almak` — admin; `manager1` и `manager2` — manager. Если отображаемое имя не задано, интерфейс показывает логин. Перед выпуском остаются настройка и выдача индивидуальных паролей; существующий аккаунт выбирается командой по логину с сохранением его ID. Пароли не записывать в документацию, git или переписку. Ограничения отдельных функций — отдельный будущий этап, сейчас их не придумывать.

## D1. Серверные черновики и переписки

### Поведение

Обычный и ИИ-черновик — один вид незавершённого заказа. Он может содержать одно поле и любое количество неполных товаров. Созданный вручную черновик тоже можно открыть с помощником. Источник данных — PostgreSQL; localStorage перестаёт быть основным хранилищем заказов и переписок.

Предлагается общая очередь для всех трёх пользователей: фильтры «Все», «Мои», поиск по клиенту/телефону/названию, автор, последний редактор, время изменения, состояние сохранения. Авторство не ограничивает доступ: в первой версии все пользователи имеют полный доступ. Подтвердить видимость общей очереди перед реализацией.

### Модель и контракты

Предлагаемые сущности:

- `order_drafts`: UUID, `schema_version`, `revision`, частичный документ JSONB, источники ручных/ИИ-полей, автор и последний редактор, даты, состояние `active` / `converted` / `archived`, ссылка на созданный заказ.
- Назначение черновика: новый заказ, повтор заказа (`source_order_id`) или изменение существующего (`target_order_id`, `base_order_revision`). Не путать исходный и созданный заказ.
- `order_conversations`: UUID, ссылка на черновик/заказ, автор, название, даты. Для MVP — одна переписка на рабочий черновик; созданный вручную черновик может не иметь сообщений.
- `order_messages`: UUID, conversation ID, автор/роль, текст, время, request ID и состояние обработки. История после создания заказа сохраняется.
- Стабильные UUID товарных строк в частичной модели; серверные числовые ID товаров не использовать как единственную идентичность черновой строки.

Предлагаемые API: список/создание/чтение/изменение/архивация черновика; постраничная история сообщений; отправка уточнения; импорт локальных записей; преобразование черновика в заказ. Точные URL и DTO утвердить в техническом контракте, например семейства `/order-drafts` и `/order-conversations`.

### План реализации

1. Согласовать единую частичную схему всех восьми типов и адаптер обычных черновиков. Не переносить ограничение обязательных полей окончательного заказа на черновики.
2. Добавить таблицы и авторизованные API. Валидировать схему, типы, размер документа и число товаров даже при разрешённых пропусках. Пустая цена не равна нулю. Поддержать версию схемы и совместимость старых записей.
3. Сохранять изменения с `baseRevision` или `If-Match`. Сравнение и запись атомарны; при конфликте — `409`, без молчаливой перезаписи. Сохранять ввод пользователя и предлагать загрузить актуальную версию/повторно применить свои правки.
4. Перенести обработку сообщения на серверный контекст: клиент передаёт текст и ID, сервер сам читает доступный черновик и источники полей. Записать сообщение до обращения к DeepSeek. Не держать транзакцию БД во время внешнего запроса.
5. Применять ответ модели только к ожидаемой ревизии и в одной транзакции с изменениями, источниками и результатом сообщения. Поздний ответ после ручной правки не затирает её. Request ID делает повторную отправку того же запроса идемпотентной.
6. Подключить оба фронтовых сервиса к общему API. Показывать «Сохраняется», «Сохранено» или ошибку. Не показывать «Сохранено» до ответа сервера. Защитить маршруты списка/редактора черновиков авторизацией.
7. Синхронизация MVP: перечитывание при открытии/возврате фокуса и ограниченный polling активного черновика/списка. WebSocket пока не обязателен. Несохранённый ввод не заменять фоновым обновлением.
8. Регистрацию заказа сделать идемпотентной: создание заказа, первоначальная оплата при явно заданной сумме и перевод черновика в `converted` — одна транзакция. Повтор запроса возвращает уже созданный order ID. Переиспользовать сервисную логику создания, не вызывать собственный HTTP API из handler.
9. Перенести существующие записи безопасным импортом по описанному ниже протоколу. Затем прекратить основной режим записи черновиков в localStorage.
10. Перед включением проверить резервное копирование новых таблиц, восстановление и выбранные сроки хранения. Архивация переписки не удаляет реальный заказ.

### Перенос локальных данных

- Предложить импорт после входа, с количеством найденных черновиков/переписок. Старые записи могут быть общими для нескольких аккаунтов одного профиля; не загружать их незаметно от имени вошедшего пользователя.
- Учесть оба формата: `order_drafts` и `ai_order_drafts_v1`, включая историю завершённых чатов и фактический редакторский `editorState.payload`, если он новее частичного документа. Нельзя потерять ручные правки, оставшиеся в принятой форме старой версии.
- Для ИИ-записей использовать исходный UUID и запись соответствия импорта. Для обычных числовых ID создать устойчивый ключ «источник/профиль импорта + локальный ID»: одинаковый номер на двух компьютерах не означает один черновик.
- Не объединять два реальных заказа только потому, что их содержимое одинаково. Конфликт одинаковых UUID с разными данными разбирать явно, не затирать более свежую серверную запись.
- Импорт повторяемый и идемпотентный, с ответом по каждой записи и поддержкой продолжения после частичной ошибки. Отметку о переносе ставить только после серверного подтверждения.
- Хранить `imported_by`; неизвестного исторического автора оставлять неизвестным. Не назначать импортирующего менеджера автором старых сообщений.
- Не удалять локальные оригиналы до проверки импорта и возможности восстановления. После успешного переноса предложить очистку отдельно. При смене аккаунта не показывать чужой локальный буфер.
- Полный offline-режим не входит в MVP. Возможный временный буфер несохранённого ввода должен быть отделён от серверного источника данных, привязан к пользователю и не создавать ложного обещания синхронизации.

### Проверка готовности

- Черновик с одним полем, обычный черновик и ИИ-переписка доступны после входа на другом устройстве.
- Два менеджера не могут незаметно затереть друг друга; конфликт сохраняет оба варианта ввода.
- Отвал сети/повтор запроса/поздний ответ ИИ не теряет текст и не создаёт дубликаты сообщений или заказов.
- Перенос обоих локальных форматов, повторный и частично завершённый импорт не теряют данные и связи.
- История завершённого заказа остаётся доступной, а архивация черновика не меняет заказ.
- Все чтения и записи требуют авторизации и проверяют права на сервере.

### Решить перед реализацией

Подтвердить общую очередь и возможность правки всеми; нужны ли назначение ответственного и передача черновика; сроки хранения; допустим ли временный локальный буфер при потере сети; кто запускает импорт старого общего профиля. Предлагаемый MVP не требует отдельной модели организаций, полноценных блокировок или совместного набора текста в реальном времени.

## O1. Повтор заказа

### Поведение

В карточке существующего заказа появляется «Повторить заказ». Нажатие создаёт **новый черновик**, не оплаченный и не зарегистрированный заказ. Открывается обычный редактор; менеджер может поменять товары вручную или уточнением в чате. Исходный заказ остаётся без изменений.

### Что переносить

| Данные | Предлагаемое правило |
| --- | --- |
| Все восемь видов товаров, размеры, количества, модели, поставщики, известные цены | Копировать, выдавая новые UUID черновым строкам; текущих цен в системе нет, старые цены требуют проверки |
| Клиент, телефон, доставка и адрес | Копировать с возможностью исправить |
| Дата заказа | Оставить пустой до выбора менеджером; явно показать, что это новый заказ |
| Комментарий | Предлагать копирование отдельно: там могут быть разовые договорённости |
| Скидка | Не переносить автоматически; предложить отдельный выбор |
| История платежей, внесённая сумма, долг, признак оплаты | Не переносить; платежи нового заказа начинаются с нуля |
| Статус исполнения, номер, даты создания/изменения, ID товаров и оплат | Не переносить; новый статус назначения применяется при регистрации |
| История старой переписки | Не копировать как новую; оставить ссылку на исходный заказ |

Точные переключатели копирования — предложение, а не уже согласованное поведение. Закупочные цены из старого заказа тоже могут устареть: их перенос нужно отдельно подтвердить.

### План реализации

1. Сделать серверную операцию «создать черновик повтора» по доступному source order ID. Читать источник на сервере, не доверять присланной клиентом полной копии.
2. Зафиксировать копируемые поля и переключатели; хранить `source_order_id` только как происхождение, без связи, изменяющей оригинал при редактировании копии.
3. Создать независимые черновые товары, обнулить служебные/финансовые данные по правилам выше, не переносить серверные ID.
4. Добавить действие в карточку заказа и короткое окно параметров копирования. Блокировать случайный двойной клик; повтор одного request ID возвращает тот же новый черновик, но отдельное намеренное повторение создаёт другой.
5. Открыть обычный редактор с подсказкой «На основе заказа №…; проверьте цены». Не давать ИИ придумывать актуальную цену.
6. Создание настоящего заказа — только отдельное подтверждение стандартным путём.

### Проверка готовности

Копирование всех восьми категорий, независимость исходника, отсутствие прежних оплат/статуса/ID, безопасный повтор запроса, отмена окна копирования без создания черновика. Новый заказ получает свой номер и историю платежей.

### Решить перед реализацией

Подтвердить дату, комментарий, скидку и закупочные цены по таблице. Уточнить, нужен ли повтор из списка заказов или достаточно карточки; предлагается начать с карточки.

## A1. Помощник для конкретного существующего заказа

### Поведение и интерфейс

В карточке заказа — действие «Изменить с ИИ». Оно открывает тот же плавающий чат, но с постоянно видимой привязкой **«Редактирование заказа №…»** и ссылкой на заказ. Любой заказ, в том числе полностью заполненный вручную, может стать исходником.

Пример: «В первой двери ширину поменяй на 70, добавь ещё одну такую же». Помощник изменяет рабочую копию. Пользователь видит список «было → стало», проверяет товарные строки и нажимает отдельное **«Применить к заказу №…»**. До этого реальный заказ не меняется. Отмена/закрытие чата сохраняет рабочую копию; удаление чата не удаляет заказ.

Историю по заказу можно открыть повторно; предлагается возвращать существующую активную рабочую копию текущего пользователя, а не создавать новый чат при каждом нажатии. Сессии редактирования разных пользователей могут быть отдельными; применение проверяет общую версию заказа. При переходе на другой заказ не перепривязывать уже открытый чат незаметно.

### План реализации

1. Ввести ревизию заказа. Все изменения, влияющие на снимок, включая товары, шапку, статус, оплаты и скидку, должны участвовать в механизме версии. Контроль внедрить также в обычное редактирование; иначе ИИ-копия может быть перезаписана старой ручной формой.
2. Создавать серверную рабочую копию по target order ID и ожидаемой ревизии: полный базовый снимок, частичная редактируемая модель, стабильные UUID строк, источники полей и история. Проверять доступ пользователя к заказу при открытии, каждом запросе и применении.
3. Построить обратный адаптер API → редактируемая модель для всех восьми типов. Сохранить несколько размеров доборов/обшивки, вторые полотна и поля, которые ИИ-схема сейчас не описывает. Не сводить сложный ручной товар к одному размеру и не терять его данные при обратной сборке.
4. Учесть существующий `PUT`: он пересоздаёт товары и их числовые ID. Для MVP UUID рабочей копии привязаны к базовому снимку; при изменении ревизии требуется явное обновление/повторное применение, а не сопоставление одинаковых товаров по порядку. При необходимости позже добавить постоянный UUID товару в БД.
5. Добавить режим серверного запроса `edit_order` с контекстом из БД и отдельными правилами предпромпта. Модель выдаёт предложение по разрешённым полям, а не выполняет API-команды. Не объявлять все поля исходного ручного заказа навсегда заблокированными: явно названные поля должны меняться; неназванные — сохраняться.
6. Показывать короткий diff с понятными названиями и идентичностью строк. Поддержать добавление/изменение/удаление товаров, уточнения и отмену последнего предложения в рабочей копии. Неоднозначное «измени дверь» при нескольких вариантах вызывает уточнение.
7. Реализовать отдельную операцию применения рабочей копии: проверить base order revision и права, валидировать итог, пересчитать суммы существующей серверной логикой, сохранить заказ и аудит в транзакции. Внешний запрос к модели не держит блокировку заказа.
8. Операция применения идемпотентна. При конфликте версии (`409`) ничего не менять, сохранить рабочую копию и показать, что заказ уже изменён. Предложить актуализировать основу и перепроверить diff. Полуавтоматическое объединение конфликтов отложить.
9. После успеха обновить карточку заказа, зафиксировать новую ревизию и применённый diff в истории. Для нового раунда правок брать новый серверный снимок, не продолжать с устаревшим базовым.

### Граница первой версии

- Предлагается разрешить шапку клиента, комментарий, доставку и товары. Изменение конкретных полей подтверждается в diff.
- Не изменять ИИ-командой историю оплат, внесённую сумму, признак оплаты или статус исполнения. Для них уже есть отдельные действия. Скидку в первом этапе оставить отдельному действию; расширить после согласования.
- При изменении товаров сохранить неизменной историю реальных платежей, заново рассчитать стоимость и долг. Не передавать устаревший `prepayment` из рабочей копии в текущий PUT, иначе бэк может создать нежелательную корректировку платежа.
- Применять изменения через сервисный метод с явным списком разрешённых полей. Не отправлять частичный JSON в endpoint полной замены заказа.
- Закупочные данные и другие поля, не требуемые для команды, не включать в контекст модели без необходимости. Это не ограничение прав менеджера, а выбор состава контекста.
- Ошибка/отмена DeepSeek не изменяет заказ; черновая переписка и предложение остаются доступны.

### Проверка готовности

Редактирование вручную созданного заказа; сохранность всех восьми категорий, нескольких размеров и вторых полотен; неизменность оплат и прочих неназванных полей; невозможность применения к другому order ID; конкурирующие изменения двух пользователей; повтор запроса применения; отмена и ошибка модели; корректные пересчёты и запись автора/ревизий/diff.

### Решить перед реализацией

Подтвердить границу полей первой версии, в особенности скидку/закупочные данные; доступ всех менеджеров к истории правок; поведение при нескольких активных рабочих копиях одного заказа. Предлагаемый MVP — отдельные рабочие копии и явная проверка общей ревизии, без незаметного переноса правок между чатами.

## 4. Общие условия выпуска

- На этапе согласования менялась только документация. R1 теперь готовится локально; рабочая БД, создание реальных аккаунтов и публикация ещё не выполнялись. Остальные функции остаются в плане.
- Каждую задачу выполнять отдельным проверяемым этапом с уточнением открытых решений перед кодом.
- Сохранять совместимость веба и Electron, форматы локальных записей до завершения импорта и доступность существующих заказов.
- Не выводить ключ DeepSeek, пароли и тексты реальных заказов в технические логи. Примеры для тестов обезличены.
- Для внедрения серверного хранения подготовить перенос и обратный путь до переключения клиентов. Откат интерфейса не должен возвращать запись в устаревшую локальную копию поверх новых серверных данных.
- Оценки сроков и даты реализации пока не назначены: сначала подтвердить решения и API-контракты.
